PharmInt Forecast Models

Reference guide to the standalone forecasting models — drug-substance × month panel, T=20 (Jan 2023–Aug 2024), target = next month's transaction count. Routing/blend models (Mixed A/C, Mixed D/C) are covered elsewhere and omitted here.

Shared setup

All models predict transaction_count for a substance one month ahead, using its own lagged counts and (for some models) covariates: median unit price, average deal size, exporter churn, destination count, and price spread. Most fit on log1p(count) and back-transform with expm1; a few work on counts directly, which turns out to matter (see Model C). Every model uses substance-specific intercepts so a 200-shipment/month generic and a 3-shipment/month niche API aren't compared on the same baseline.

Model A — AR(1) / AR(2), substance fixed effectseconometric

y_dt = α_d + φ₁·y_{d,t-1} (+ φ₂·y_{d,t-2}) + ε_dt

The benchmark. A linear autoregression of each substance's own log-count history on itself, with a per-substance intercept α_d absorbing its baseline size. Estimated by within (fixed-effects) OLS: subtract each substance's mean before fitting, so the slope φ is identified purely from month-to-month movement, pooled across all substances (no single substance has enough history to estimate its own φ). Both AR(1) and AR(2) are fit and compared; AR(1) is the version carried forward.

Known bias. The within transform mechanically correlates the lagged term with the residual (Nickell bias), pulling φ toward zero more than the truth warrants — worse the shorter the panel. Model D exists to correct this.

Model B — dynamic panel with covariates + month effectseconometric

y_dt = α_d + λ_t + φ₁·y_{d,t-1} + φ₂·y_{d,t-2} + β'X_{d,t-1} + ε_dt

Model A plus two additions: month effects λ_t (absorb anything hitting every substance at once — a port disruption, a rupee move) and lagged covariates X (price, deal size, exporter churn, destinations, price spread). Designed to be estimated by Arellano–Bond GMM (see Model D) since a lagged dependent variable plus fixed effects biases plain OLS either direction — but in practice the GMM version is unstable here (weak/exact-identified instruments), so what's reported as Model B is the FE-OLS fit with its bias flagged rather than a fragile GMM point estimate.

Model C — PPMLeconometric

E[count_dt | ·] = exp( α_d + φ₁·y_{d,t-1} )

PPML = Poisson Pseudo-Maximum-Likelihood. It fits a Poisson-shaped regression (mean = exp(linear predictor)) to the count directly, but doesn't actually assume the data are Poisson-distributed — "pseudo" because it's used as a quasi-likelihood: the estimator stays consistent as long as the conditional mean is correctly specified, even if the true variance is very different from a Poisson's (which it is here — shipment counts are far more dispersed). This is the standard fix for exactly the problem Models A/B/D have: fitting log1p(count) and inverting with expm1 doesn't recover the true mean under skew (Jensen's inequality bites), so those models forecast systematically low. PPML also needs no +1 offset for the zero-transaction months, which A/B/D's log1p requires and which is itself an arbitrary tuning choice.

PPML fixes scale and bias, not the dynamic-panel bias — it still carries the same Nickell-type bias as A and B on φ₁. Use C when the total (aggregate forecast) matters; use D when the per-substance ranking matters.

Model D — Arellano–Bond difference GMM, correctedeconometric

Δy_dt = φ₁·Δy_{d,t-1} + Δε_dt   instrumented by y_{d,t-2}

GMM = Generalized Method of Moments. Rather than maximizing a likelihood or minimizing squared error directly, GMM picks parameters that make a set of chosen "moment conditions" — here, that an instrument is uncorrelated with the error — as close to zero as the data allow. It's the right tool when a variable you'd like to use as a predictor (the lagged count) is itself correlated with the error term, which is exactly Model A's Nickell-bias problem.

Mechanically: first-difference the equation to eliminate the fixed effect α_d without inducing the within-transform correlation, then instrument the endogenous differenced lag with an even-older level (y_{t-2}) that correlates with the regressor but not with the new error. This is the same idea as Model A, but with the bias that A leaves in deliberately removed.

On this panel, φ₁ for D is statistically indistinguishable from zero — the central empirical finding: month-to-month transaction counts carry no exploitable pooled momentum once the bias is corrected. A's negative φ₁ is mostly that same bias, not real information.

The tree/ML models

Models E, F and G all use gradient boosting: an ensemble of shallow decision trees built one at a time, where each new tree is fit to the errors the ensemble so far still gets wrong. Unlike the linear models above, boosted trees can pick up nonlinear interactions between features (e.g. "churn only matters when price spread is also high") without anyone specifying that interaction by hand.

Model E — GBMML

A gradient-boosted tree ensemble (XGBoost), used as a direct, standalone regressor on the same lag/covariate features Models A–D use — no linear-model scaffolding underneath it. Included mainly as a baseline for "how far can raw ML get with no econometric structure." Answer on this panel: not very far — it performs worst of the group, consistent with the general rule that 20 monthly observations per substance is a short sequence for a model with no built-in notion of what a lag or a fixed effect is; it has to learn those patterns from scratch.

Model F — GMM + XGBoost residual correctionML + econometric

XGBoost ("Extreme Gradient Boosting") is a specific, heavily optimized gradient-boosting implementation — regularized to resist overfitting and fast on tabular data. Here it isn't predicting the target directly; it's trained on Model D's own leftover residuals (the GMM prediction's errors, on the log scale) as a function of the same lag/covariate features. The idea: if the linear GMM model is systematically wrong in some describable way (e.g. it under-predicts for high-churn substances), XGBoost can learn that pattern and the correction gets added back onto the GMM's forecast. So Model F = Model D's forecast + a learned error correction, not a replacement for it.

Model G — GMM + XGBoost + LightGBM ensembleML + econometric

LightGBM is another gradient-boosting framework, similar in spirit to XGBoost but built around histogram-binned features and leaf-wise (rather than level-wise) tree growth, which makes it faster on larger data and sometimes finds different splits than XGBoost on the same problem. Model G fits three predictors independently — the GMM log-linear model, XGBoost, and LightGBM (the latter two as direct count regressors, same features as Model E) — and simply averages their three predictions on the count scale. It currently scores best of every standalone model here: the average smooths out each individual model's idiosyncratic errors better than any one of them alone.

"Model F" — LSTMML

LSTM (Long Short-Term Memory) is a recurrent neural-network architecture with gated memory cells designed to learn patterns across a sequence over time, rather than treating each row independently the way a tree model does. Here, each substance's month-by-month count history is fed in as a sequence. It's included as the "deep learning" option, with the caveat — stated up front in its own code — that a 20-month-per-substance sequence is short for a model class that typically wants much longer sequences to find its footing; that shows up in its results, currently the weakest of all nine models.

Naming collision, not a typo: this LSTM model and the GMM+XGBoost model above are both internally labeled "Model F" — they were built in separate scripts that each picked the next free letter independently. The comparison table disambiguates them as Model F (GMM+XGB residual) and Model F (LSTM).

Seasonal models: is the panel long enough to model an annual cycle yet?

At T=20 months, the two-model spec's own roadmap says seasonality "becomes visible" — but 20 months is only Jan 2023–Aug 2024: Jan–Aug appear twice, Sep–Dec only once. Two models were built to test whether that's enough, implemented in Models/model_seasonal.py.

Model H — Fourier-seasonal Arellano-Bond GMMeconometric

Δy_dt = φ·Δy_{d,t-1} + γ₁·Δsin(2πm_t/12) + γ₂·Δcos(2πm_t/12) + Δε_dt

Model D's spec, plus two deterministic calendar terms — sine and cosine of calendar month — added straight into the differenced equation. Because they're known functions of the calendar rather than lagged data, they need no instrumenting, unlike the endogenous lag. This was chosen over 12 separate calendar-month dummies specifically because several months (Sep–Dec) appear only once in the panel — too thin to identify a dummy each, but fine for two smooth, pooled coefficients shared across all 792 substances.

Result: MASE 0.89, about level with Model D's own score — not a win. The seasonal coefficients aren't statistically significant (p ≈ 0.17–0.23). Expected: with under two annual cycles of data, there isn't enough repetition yet to pin down a seasonal effect with confidence. Safe to keep (doesn't hurt), not yet earning its complexity.

Model I — SARIMAclassical time series

SARIMA (Seasonal ARIMA) is the classical approach to this problem: an autoregressive term plus a seasonal autoregressive term at a 12-month lag, fit directly on each series. Unlike every other model here, it is not pooled — each drug substance gets its own independent fit, so it can't borrow strength across substances the way Models A–H do. Tried two ways, matching the project's existing pattern of reporting both an aggregate and a per-entity result:

  • Aggregate — one SARIMA on the total market (all substances summed per month). MASE 3.81 — nearly 4x worse than doing nothing. The fit itself is a tell: the autoregressive coefficient comes out at 1.01, essentially a unit root (non-stationary), estimated from only 19 monthly observations with a seasonal lag of 12 — barely 1.6 cycles to find a seasonal pattern in.
  • Per substance — one SARIMA per drug substance, only for the ~716 substances with at least 15 months of history (substances below that are excluded from this model's score, not silently defaulted). MASE 1.43 — also worse than naive, for the same reason at even smaller scale: each individual fit has even less data to work with than the aggregate did.
Included for transparency, not use. Both variants lose to a naive forecast. This isn't a bug in the implementation — it's the expected result of asking a method built for long single series (SARIMA usually wants several full seasonal cycles, i.e. years of monthly data) to work with 20 months split into either one aggregate series or hundreds of thin per-substance ones. Revisit once the panel covers 2+ full years.

Backtesting: does the model hold up with less data?

All results above use the full T=20 panel. To check whether the models are actually reliable — or just got lucky with 20 months — backtesting/run_backtest.py truncates the panel to the first N months and reruns Models A–D and F/G unmodified (both already size their train/validate/test split off however many months are in the panel, so feeding them a shorter panel is the backtest). Windows tested: 3, 6, 9, 12, 15, 18, 20 months.

At 3 months there isn't enough history for the models' own train/validate/test split to produce a train window at all — skipped automatically. At 6 months, every model fails outright with "regressors do not have full column rank": the GMM instrument matrix needs more history than 6 months gives it. Both are expected, not bugs — the models need roughly 9+ months before there's enough data for GMM to even run.

Why every model dips at the 15-month window

Every model gets worse at 15 months and better again at 18–20 — at first glance that looks like instability. It isn't: it's one weird month for a couple of big drugs, not the models breaking down. Comparing the naive (repeat-last-month) error split by substance size makes this concrete — the top ~60 substances by volume account for almost all of the count-scale error at every window, and their error specifically spikes at the 15-month test month:

MASE and RMSE(count) are both raw-count-scale metrics, so they're dominated by whichever substances have the biggest volumes — a bulk order or "tender" landing oddly in one substance that month (see the Model D note above on tenders) is enough to drag the whole test month down. It's a property of that one calendar month, not evidence the model degrades with more data.

Why RMSE(log) drifts up at 18–20 months instead

RMSE(log) tells a different story because it averages error equally across substances rather than weighting by volume — so it's dominated by whoever's numerous, not whoever's big. The number of small, thinly-traded substances (previous month's count under 5) keeps growing as the panel gets longer, simply because more products have launched by month 18–20 than by month 9–12:

Each small substance's own log-error stays roughly flat (~0.63–0.68) at every window — going from selling 1 unit to 3 is a huge relative move even though it's nothing in real volume, and that's just inherently noisy to call. What changes is there are ~40% more of these substances by t=18–20, and since RMSE(log) doesn't weight by size, more noisy small substances in the average pulls the number up. No individual substance is being forecast worse — there are just more hard-to-predict small ones in the mix later on.

Takeaway. MASE/RMSE(count) and RMSE(log) are measuring different failure modes — one calendar month's big-substance volatility vs. a growing population of small, noisy substances — not disagreeing about whether the model works. Neither swing means the model is flip-flopping in quality; both are structural properties of the data at that window, and both fade back out once the anomalous month or the substance mix normalizes.

Data pipeline: Excel → MongoDB → dashboard

Excel and MongoDB serve different ends of the same pipeline, not overlapping roles.

1M shipment rows (Data/combined_export_dataset.parquet) → Code.py (cleaning / mapping / aggregation) → forecast/history/comparison tables (.csv, "Code results/" + "Forecasted results/") → dashboard/scripts/ingest.py → MongoDB Atlas → Next.js dashboard

Parquet/CSV is the offline exchange format: Code.py reads the ~1M-row source file (a .parquet file) and writes its aggregated outputs as CSVs. Nothing in the running dashboard reads any of these files directly.

MongoDB Atlas is the live datastore. ingest.py loads those CSVs into collections (forecasts, history, drugs, countries, models), and the dashboard queries only this database at runtime. This replaced an earlier static-JSON-bundled-with-the-app approach, so the site's data now refreshes by re-running npm run ingest instead of a redeploy.
