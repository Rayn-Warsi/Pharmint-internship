PharmInt ETL Pipeline

Raw shipment records → six pre-aggregated analytics collections. Source: backend/scripts/etl-pipeline.js

The pipeline reads raw pharmaceutical export shipments, drops low-quality rows, enriches each record, then runs six independent MongoDB aggregations to build the collections the app reads from. Every collection is rebuilt from the same filtered source — there is no row-by-row processing in application code.

1. The big picture

One source collection feeds six aggregation jobs. Each job groups by a different key and writes its own analytics collection. The app never queries raw shipments — it reads these outputs.

2. Run order

The entry point runETL() connects to both databases, builds the filter once, then calls the six generators in sequence. Test mode processes a single year and skips exporter_directory (which needs all years to be correct).

Invocation:

node etl-pipeline.js --test --year=2024   # single year, no exporter dir
node etl-pipeline.js --full               # all years 2022-2025
node etl-pipeline.js --full --no-clear    # append instead of rebuild

3. Stage 1 — Quality filters

A single filter object in qualityFilters.js is $matched at the head of every aggregation, so all six outputs see the exact same clean rows. A row survives only if all of these hold:

  • Currency present and non-empty (any currency — USD values are pre-converted in the source).
  • Unit price present and not one of '' '0' 0 null nan N/A NOT KNOWN NULL, and after casting to double is > 0 and ≤ 1000 (the ceiling rejects entries where a shipment total was pasted into the per-unit field).
  • Quantity present and non-zero.
  • Destination is a real foreign country — excludes INDIA (domestic), plus empty / N/A / NOT KNOWN.
  • Product description passes six regex filters that strip biological samples, generic "harmless medicine" boilerplate, category labels, veterinary/non-pharma items, invoice admin text, and format-variant junk.

4. Stage 2 — Enrichment

Each generator adds computed fields with $addFields before grouping. Three matter most:

  • FOB with fallback — safeToFOB(): use FOB_VALUE_USD when it's valid, otherwise estimate QUANTITY × UNIT_PRICE_USD. This recovers ~23K rows that would otherwise have no trade value.
  • FOB estimated flag — isFOBEstimated() returns 1/0 so each output can report what share of its value was estimated in a data_quality sub-document.
  • Country normalization — only in country_market_intel, a MongoDB $switch collapses variants (DRC, Congo Kinshasa, USA/US, UK/Britain, misspellings) to canonical names so they don't split into separate rows.
Worth flagging for study. The $switch normalization runs only inside the country generator. The other five collections still group on the raw DESTINATION_COUNTRY/PRODUCT_DESCRIPTION, so the same country can appear under several spellings there. A standalone normalizeCountry() JS function exists in the file but is never called by the aggregation.

5. Stages 3–5 — Group, shape, insert

Every generator follows the same three moves: $group on its key, $project to shape the final document, then insertMany. The pipeline uses accumulators ($topN, $percentile, per-currency counters) instead of $push to keep memory bounded on millions of rows.

6. Clear-and-rebuild behavior

By default each generator clears before writing, so a run is idempotent. The scope of the clear differs, which is the subtle part:

  • Year-scoped (product, country, price-trends, regional): delete only rows for the year being processed — safe for incremental single-year runs.
  • Full wipe (exporter_directory, market_opportunities): always deleteMany({}) because they aggregate across all years; run these with --full only.
  • --no-clear skips deletion entirely (append mode).
